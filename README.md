# 编程题诊断 Agent

一个以**判题沙箱为 ground truth** 的编程题诊断 Agent：学生提交代码 → 自动判题 →
定位错因 → 生成**可验证**的讲解 → 推荐针对性练习 → 跟踪掌握度。

核心原则：**所有 ground truth 由验证器提供，不依赖人工标注。**

### 变异数据集（错因标签的来源）

错因标签不靠人工标注，而是**构造出来的**：往参考解里注入已知类型的错误，
注入的是什么错，标签就是什么错；再用判题机确认「这样改确实会失败」。

| 算子 | 错因标签 | 候选 | **有效样本** | 等价变异率 |
| --- | --- | --- | --- | --- |
| off_by_one_minus | 差一错误（偏小） | 688 | **586** | 14.8% |
| off_by_one_plus | 差一错误（偏大） | 688 | **576** | 16.3% |
| arithmetic_operator | 算术运算符误用 | 542 | **497** | 8.3% |
| condition_negation | 条件判断取反 | 382 | **378** | 1.1% |
| comparison_operator | 比较符误用 | 376 | **367** | 2.4% |
| argument_order | 参数顺序错误 | 265 | **216** | 18.5% |
| return_value | 返回值错误 | 132 | **120** | 9.1% |
| boundary_condition | 边界条件错误 | 184 | **90** | **51.1%** |
| boolean_operator | 逻辑运算符误用 | 85 | **77** | 9.4% |
| initial_value | 初始值错误 | 81 | **71** | 12.3% |
| loop_control | 循环控制错误 | 20 | **9** | 55.0% |
| **合计** | | **3,443** | **2,987** | **13.2%** |

覆盖 512 道题，判定分布 WA 2511 / RE 418 / TLE 58，全量生成耗时 94 秒。

**等价变异率是个有价值的副产品。** 它指的是「注入错误之后，测试用例仍然全部通过」
的比例——说明这个改动在当前测试下不改变行为，或者测试根本没覆盖到那处分支。
它衡量的是**测试用例对错误的检出能力**。

这里的结果很说明问题：`边界条件错误` 的等价变异率高达 **51.1%**，而
`比较符误用` 只有 2.4%。也就是说，**把 `<` 改成 `<=` 有一半的概率不会被官方测试发现**，
而把 `==` 改成 `!=` 几乎立刻被抓。这正好印证了学界对 HumanEval / MBPP 测试用例
覆盖不足的批评：单点测试多，边界测试少。

## 架构

```
                    ┌──────────────────────────────┐
                    │        CodeVerifier          │  判题器：组装下面几层
                    └───────┬──────────────┬───────┘
                            │              │
              ┌─────────────▼───┐     ┌────▼─────────────┐
              │   languages     │     │     compare      │
              │ 源码名/编译/运行 │     │ exact/token/float│
              └─────────┬───────┘     └──────────────────┘
                        │
              ┌─────────▼──────────────────────────┐
              │            Sandbox                 │  同一接口，两种实现
              ├────────────────┬───────────────────┤
              │  LocalSandbox  │  DockerSandbox    │
              │  子进程+rlimit │  容器+cgroup      │
              └────────────────┴───────────────────┘
                        │
              ┌─────────▼───────────┐
              │  _proc.run_process  │  并发读管道 / 看门狗 / rusage
              └─────────────────────┘
```

分层原则：**沙箱只负责「安全地跑一个命令，如实报回资源消耗」，不做任何对错判断**；
判定逻辑全部在 verifier。换沙箱不影响判题语义，加语言不用改判题器。

### 两种沙箱的能力差异

| 能力 | LocalSandbox | DockerSandbox |
| --- | --- | --- |
| 墙钟超时 | ✅ 看门狗 + 杀进程组 | ✅ 同左，并额外 `docker kill` 容器 |
| CPU 时间限制 | ✅ `RLIMIT_CPU` | ✅ `--cpus` + `RLIMIT_CPU` |
| 内存上限 | ❌ macOS 上做不到（见踩坑 2） | ✅ `--memory`，cgroup 强制 |
| 网络隔离 | ❌ | ✅ `--network none` |
| fork 炸弹防护 | ❌ | ✅ `--pids-limit`（按 cgroup） |
| 峰值内存上报 | ✅ `wait4` 精确到该子进程 | ✅ |
| 适用场景 | 开发、单测、跑可信代码 | 跑不可信代码 |

## 诊断闭环

### 核心思路：把诊断变成可验证的搜索

常见做法是让模型看一眼代码、猜一个错因。这里换了个思路：

```
判题失败
   │
   ├─ 生成单点修复候选（复用变异算子——算子大多自反，对错误代码施加一次就得到修复）
   │
   ├─ 每个候选交给判题机**实跑一遍**
   │
   └─ 有候选通过全部用例 → 这个改法就是被证明的修复
         同时得到错因类型 + 出错行号 + 具体改法
```

**结论不是「模型觉得这里是边界错误」，而是「把这里改掉之后，全部用例都过了」。**
这条保证被一个测试锁住了：`test_every_reported_repair_really_passes_the_judge`
——报告里给出的每一个修复，都必须真的能跑通。

### 实际输出

```
$ python scripts/diagnose.py --file submissions/sum_two/wrong_answer.py --problem sum_two

诊断：算术运算符误用（已通过判题机验证）
位置：第 5 行
改动：a - b  →  a + b

依据：用例 c1 失败（第 1 项不符：期望 3，实际 -1）。
      把这一处改成上面的写法后，3/3 条用例全部通过。

说明：这个结论不是猜的——系统真的把那处代码改掉、重跑了一遍所有测试用例。
```

### 定位不到的时候会说什么

```
诊断：未能定位到可验证的单点错误

已知线索：
  · 用例 c2 失败（第 1 项不符：期望 -1，实际 0）
  · 期望输出：-1
  · 实际输出：0

系统试了 17 个单点修复候选都没能让全部用例通过。这说明错误可能不止一处，
或者需要调整整体思路——这种时候给一个「看起来合理」的结论反而会误导，
所以这里不做猜测。
```

**宁可承认不知道，也不编一个听起来合理的理由。** 教学场景里错误的知识比没有知识更糟，
所以「未定位」是一个正式设计的输出，不是失败兜底。

### 评估结果（200 条样本，来自 153 道题）

错因标签在构造时就已确定，所以可以直接算准确率：

| 指标 | 结果 | 说明 |
| --- | --- | --- |
| **定位成功率** | **93.0%** | 找到了能让全部用例通过的单点修复 |
| 错因类型准确率 | 85.5% | 在定位成功的样本上 |
| 修复改动准确率 | 71.5% | 找到的修复恰好撤销了注入的改动 |
| 端到端准确率 | 66.5% | 含未定位样本 |
| 单条诊断耗时 | 591 ms | 平均尝试 8.6 个候选 |

耗时主要花在「每个候选都真跑一遍判题机」上（单次判题约 77 ms）。
这是可验证性必须付的代价，如实写在这里。

### 一个反直觉的发现：修复不唯一

错因类型准确率 85.5%、修复改动准确率 71.5%，这个差值不是「定位错了」——
**系统报告的每一条修复都真的通过了全部测试**，只是找到的可能是
**另一种也能通过的改法**。

为了验证这个解释，做了个留出实验：把「条件取反」算子从修复候选里排除，
模拟「系统没见过这类错因」：

| 注入错因 | 候选包含该算子 | 候选排除该算子 |
| --- | --- | --- |
| 条件取反 | 定位成功率 100% | **定位成功率 38.5%** |

剩下那 38.5% 也不是真的定位成功：它们是**被别的算子的改法蒙对的**——
改一个完全不同的地方，测试也过了。

**这说明的其实不是诊断系统的问题，而是测试用例的问题**：当多个语义不同的改法
都能让测试通过时，说明这套测试不足以区分它们。这和前面测出的
「边界条件错误等价变异率 51.1%」是同一个现象的两面——一个从注入侧看到它，
一个从修复侧看到它。

## 掌握度建模与针对性出题

把「单次诊断」变成「持续陪练」需要知道两件事：学生弱在哪，下一题该练什么。

### 技能映射不用人工标注

变异数据集已经把这个信息生产出来了：**某道题能检出 k 类错误，说明它的测试确实
能考察 k 这项技能。** 于是 512 道题自动获得技能标注，覆盖 11 项技能：

| 技能 | 可考察题目数 | 技能 | 可考察题目数 |
| --- | --- | --- | --- |
| 差一错误（偏大/偏小） | 356 / 355 | 边界条件错误 | 79 |
| 算术运算符误用 | 324 | 返回值错误 | 70 |
| 条件判断取反 | 265 | 逻辑运算符误用 | 67 |
| 比较符误用 | 262 | 初始值错误 | 58 |
| 参数顺序错误 | 182 | 循环控制错误 | 7 |

同一份变异数据既做错因标签、又做技能标注，而且技能名称和诊断输出用的是同一套词表
——学生看到的用词前后一致。

### 掌握度模型：Beta-Binomial

每项技能维护一个 Beta(α, β) 后验：能做该技能的题上没犯这类错 → α+1，犯了 → β+1。
掌握度取后验均值，不确定度取后验标准差。

选这个模型的理由：

1. **自带不确定度**。练过 1 次和练过 30 次，均值一样但可信程度完全不同。
2. **可解释**。均值就是「没犯错的次数 / 总次数」的平滑版本，能直接讲给学生听。
3. **不过拟合**，几十行写完，当前的数据量也撑不起更复杂的模型。

### 一个关键设计：选下一题和下结论，用的是两个不同的判据

这是实现过程中最有价值的一处修正。最初只用「下界最低」一个判据，结果系统
**反复练同一个弱项，永远发现不了别的短板**——因为没练过的技能压根不在状态里。

修好之后仍然不够：选下一题和下结论的诉求其实相反。

| 场景 | 判据 | 原因 |
| --- | --- | --- |
| **选下一题** | 悲观下界（均值 − 0.5×标准差） | 没练过的技能不确定度最大、下界最低，会被优先补测——这就是探索 |
| **下结论** | 后验均值，且要求练过 ≥2 次 | 否则「最弱技能」永远指向那个「还不知道」的技能，结论没有意义 |

### 对照实验：先广后窄 vs 只练聚焦题 vs 随机出题

选题时优先挑「只考一项技能」的题会更好吗？测下来发现**不是**——它练习效率高，
但早期认弱项反而慢（8.11 步 vs 随机 6.64 步），因为覆盖面太窄，
很多技能迟迟攒不到证据。

于是改成「先广后窄」：已知技能覆盖率不足 60% 时优先选能一次覆盖多项技能的题，
把画像铺开；覆盖够了再收窄做针对性训练。40 个模拟学员、每人 60 次练习的对照结果：

| 指标 | **先广后窄** | 只练聚焦题 | 随机出题 |
| --- | --- | --- | --- |
| 弱项识别准确率 | **78%** | 75% | 68% |
| 认对弱项平均需要几步 | **4.39** | 8.11 | 6.64 |
| 练习中命中弱项的比例 | **67%** | 39% | 40% |
| 达到掌握阈值的比例 | **100%** | 100% | 75% |
| 达标平均练习次数 | **10.18** | 14.62 | 16.00 |

先广后窄在所有指标上都胜出，达标所需练习量比随机出题少 **36%**。

**注意这是模拟实验**：学员按固定错误概率抽样、练习后错误率边际递减。
它能说明机制按预期工作，**不能说明对真实学生的效果**——后者需要真实用户数据。
这一点在报告输出里也会打出来，避免被误读。

## 踩坑记录（面试可直接讲）

这十一个问题都是实测撞出来的，现象、原因、修法都有。

### 1. 先 `wait()` 再读输出 → 整个判题卡死

**现象**：跑一个会打印大量内容的提交，判题进程直接挂住不动。

**原因**：管道的缓冲区只有 64KB。子进程写满之后阻塞在 `write` 上，等着有人读；
而父进程在 `os.wait4` 上等子进程退出。双方互等，死锁。

**修法**：开**两个读线程**并发消费 stdout/stderr，并且读取时就带上限，
超过上限的部分丢弃并标记 `output_truncated`——既解决死锁，也顺手实现了输出超限判定。

### 2. macOS 上 `setrlimit(RLIMIT_AS)` 无法限制内存

**现象**：想给子进程设 256MB 内存上限，结果 `preexec_fn` 直接抛异常，
连 `python3 -c "print(1)"` 都起不来。

**原因**：macOS 的 `setrlimit(RLIMIT_AS)` 在新上限低于**当前已用虚拟内存**时
返回 `EINVAL`；而 Python 进程的虚拟地址空间本来就远大于这个值。实测把上限设到
4GB 依然失败。

**修法**：本地沙箱放弃强制内存上限，只**如实上报峰值**（`wait4` 的 `ru_maxrss`），
并在 `Sandbox.enforces_memory` 里如实声明能力；真正的内存限制交给容器 cgroup。
**结论是「能力要如实声明」，而不是假装限制住了。**

### 3. 用 `RLIMIT_NPROC` 防 fork 炸弹，把 C++ 编译搞挂了

**现象**：加上进程数限制之后，所有 C++ 提交都报编译失败：
`clang++: error: unable to execute command: posix_spawn failed: Resource temporarily unavailable`。
编译耗时只有 14ms——根本没到编译器真正干活就挂了。

**原因**：`RLIMIT_NPROC` 统计的是**整个用户**的进程总数，不是这个进程树。
机器上本来就跑着几百个进程，阈值一设成 128，子进程再 fork 就必然失败，
而 clang 需要派生 cc1、ld 等子进程。

**修法**：本地沙箱去掉 `RLIMIT_NPROC`，防 fork 炸弹改用容器的 `--pids-limit`
（按 cgroup 统计，语义才对）。**「按用户统计」和「按进程树统计」是两种语义，
用错了会误伤。**

### 4. 编译产物用相对路径，检测可执行文件时查错了目录

**现象**：C++ 编译成功（264ms），但运行阶段报 `命令不存在：./main`，判定变成 IE。

**原因**：判断可执行文件是否存在时用了 `os.path.exists("./main")`，
这是相对**父进程当前目录**解析的，而不是沙箱工作目录。

**修法**：相对路径（`./main`、含分隔符的路径）一律相对 `request.workdir` 解析。

### 5. 单位陷阱：`ru_maxrss` 在 macOS 是字节，在 Linux 是 KB

**现象**：一个只打印一行的 Python 程序，内存上报 11714560 "KB"（11GB）。

**原因**：macOS 的 `ru_maxrss` 单位是字节，Linux 是 KB，代码里换算方向写反了。

**修法**：按平台除 1024 或 1，统一成 KB。修正后实测：空跑 ~9MB，
分配 200MB 的程序上报 208MB，符合预期。

### 6. 把 `check()` 拆成多条独立进程，共享状态丢了

**现象**：HumanEval 164 道题里有 4 道参考解跑不过，报
`NameError: name 'rng' is not defined`。

**原因**：一开始为了「精确归因到哪条断言挂了」，我把 `check()` 函数体里的每条
语句拆成独立进程执行。但函数体里的语句是**共享局部变量**的——前面定义了
`rng`，后面的断言才用它，换进程后这个名字就不存在了。

**修法**：改成**一个进程按顺序跑完所有语句、逐条记录结果**，状态自然保留，
顺带把进程数从 7 倍降到 1 倍，单题耗时从 154ms 降到 23ms。
归因精度没有损失——驱动每跑完一条就落盘一次结果。

### 7. 模板里的双花括号：生成的代码把字典写成了集合

**现象**：591 道题的参考解**全部失败**，报 `TypeError: unhashable type: 'dict'`。

**原因**：驱动模板原本用 `str.format` 拼装，字典字面量写了 `{{"k": v}}` 转义；
后来改用 `str.replace` 替换占位符，双花括号就不再被转义了，生成的代码变成
「集合里装一个字典」——字典不可哈希，直接 TypeError。

**修法**：改成单花括号，并补了一个测试 `ast.parse(build_driver(...))`
——**生成代码的正确性不能靠肉眼，只能靠拿去编译一次**。
这个测试在后续改动里立刻拦住过一次同类问题。

### 8. 同一个工具函数用在了两个语义不同的地方

**现象**：变异引擎对简单的单行函数能产出变异体，但对真实的多语句函数
**一道题都产不出来**——3443 个候选变成 0，而且不报任何错，静默全部丢弃。

**原因**：我写了一个 `_unparse()`，里面用 `" ".join(text.split())` 把换行压成空格，
本意是给报告生成「单行摘要」。但它同时被拿去生成**变异体源码**了，于是
```
def f(n):
    total = 0
    return total + n
```
被压成 `def f(n): total = 0 return total + n` —— 这不是合法 Python，
后面的语法检查把每一个变异体都判为无效并静默跳过。
单行函数（`def f(n): return n + 1`）恰好压完仍然合法，所以小测试全过，
真实代码全挂。

**修法**：拆成两个函数——`_render_source()` 保留换行用于生成可执行代码，
`_render_inline()` 压成单行用于展示。并补了一条断言「变异体必须含换行」的测试。
**教训：展示用的格式化和执行用的生成，绝不能共用一个函数。**

### 9. 指标本身也会骗人：拿行号做对比，准确率直接腰斩

**现象**：诊断闭环的「出错行号准确率」只有 47.5%，看起来像是定位得很差，
但人工看几条结果，位置明明都是对的。

**原因**：变异体是用 `ast.unparse` **重新渲染**过的，行号会被重排。
数据集里记的行号来自**参考解**，诊断报的行号来自**变异体**，
两者根本不在同一套编号上——比较的是两个无关的数字。

**修法**：改成语义口径——比较**改动内容**：「找到的修复是不是恰好把注入的
改动反向撤销了」（注入 `a + b → a - b`，正确的修复就是 `a - b → a + b`）。
这个口径与编号无关，得到的修复改动准确率 71.5% 才是真实水平。

**教训**：评估指标本身要先被验证。一个错误的指标会让人朝着错误的方向优化，
而且比代码 bug 更难发现——代码错了会报错，指标错了只会安静地给出一个偏低的数字。
（真实诊断场景里不存在这个问题：报告的行号就是学生文件里的行号。）

### 10. 学生失败一次，十项技能的掌握度全部上升

**现象**：接上交互入口之后，跑演示时发现一份**完全没有实现功能**的代码提交上去，
系统给出「未定位」——这是对的——但个人档案里十项技能的掌握度**全部从 50% 涨到 67%**，
评价全是「基本掌握」。

**原因**：掌握度的更新规则写成了「这次作答里没有犯 k 类错误，就算 k 的一次成功」。
而诊断未定位时 `fault_operator` 是空的，于是**每一项技能都被算成了成功**。
学生明明失败了一次，档案却显示他全面进步。

**修法**：把三种情况拆开——

| 作答结果 | 更新 |
| --- | --- |
| 通过 | 该题覆盖的每项技能各算一次成功 |
| 未通过，定位到错因 k | 只有 k 记一次失败（其余技能不给分，因为这次失败可能掩盖了它们） |
| 未通过，未定位 | **什么都不更新** |

**教训：没有信息就不更新，比假装有信息安全得多。** 一个错误的信号会被反复放大——
它会污染掌握度、进而污染推荐、再污染下一轮数据。

### 11. 推荐了一项「系统自己诊断不了」的技能

**现象**：交互入口第一次跑起来，第二条推荐是「针对『循环控制错误』选一道题」。
但「循环控制错误」对应的算子是「把 break 删掉」，**不可逆**——诊断时无法从错误代码
恢复出被删掉的 break，所以系统永远给不出这类结论。

**后果**：学生真犯了这类错，系统只会说「未定位」；这项技能的掌握度也永远收不到有效信号，
变成一个只涨不跌、永远停在先验上的僵尸指标。

**修法**：在出题前强制过滤——**不能诊断的技能不出题**。技能图谱里保留它（供参考），
但推荐池和执行实验用的技能表都先过一遍 `filter_tutorable()`。

**教训**：能力边界要在**产生承诺的地方**执行，而不是在出错的地方补救。
推荐系统说「练这个」，就是承诺「我能评估你练得怎么样」；两者必须同时成立。

## 与 `data-agent` 的关系

两个项目**独立开发、独立部署、独立管理仓库**：没有代码依赖，不互相 import，
任何一个单独 clone 下来都能自己跑起来。它们共享的是一套「验证器优先」的方法论，
而不是实现：

| | `data-agent`（数据分析 Agent） | `code-judge-agent`（本仓库） |
| --- | --- | --- |
| 场景 | 数据分析工作流 | 编程题诊断与陪练 |
| 核心验证器 | 结果集精确比对（SQL 执行结果） | 判题沙箱（编译 + 测试用例） |
| ground truth 来源 | 标准 SQL + 合成数据集 | 题目自带测试用例 + 变异测试 |
| 需要自己建的基础设施 | 评测执行器、LLM-as-judge、OTel 轨迹、幂等键、CI 门禁 | 判题核心、评测执行器、CI 门禁 |

**借鉴什么、怎么借鉴**：值得迁移过来的是那套评测方法论的方向——
用确定性验证器做硬指标、给每个指标拆出能定位失败的中间量、
把评测写成 pytest 断言接 CI 门禁、以及「先建评测集再开发」的顺序。

**本项目的差异**：判题沙箱比 SQL 结果集更适合做精确比对（编译通过与用例通过
是二值的），所以主指标可以是纯确定性的通过率，不必依赖 LLM 评委。
这也是两个项目不该共用同一个评测实现的原因——验证器的性质不同，
评测设计就该不同。
