# 项目方案：编程题诊断与陪练 Agent

> 定位：学生提交代码 → 自动判题 → 定位错因 → 生成**可验证**的讲解 → 推荐针对性练习 → 跟踪掌握度。
> 核心原则：**所有 ground truth 由验证器提供，不依赖人工标注，也不依赖个人领域知识。**

---

## 一、一句话定位（简历和面试都用这句）

> 一个以判题沙箱为 ground truth 的编程题诊断 Agent：用变异测试自动构建错因评测集，并把「讲解是否正确」也纳入自动验证。

这句话里有三个差异化点：**沙箱判题**（工程深度）、**变异测试自动造标签**（评测能力）、**讲解可信性验证**（别人没有）。

---

## 二、数据源清单

### 2.1 题目与测试用例（优先公开数据集与官方 API）

| 来源 | 内容 | 获取方式 | 适用阶段 |
| --- | --- | --- | --- |
| **HumanEval / MBPP** | 各 164 / 974 题，函数级，含测试 | 公开数据集 | **第 1–2 天跑通链路** |
| **CodeContests（DeepMind）** | 约 1.3 万题，**含官方测试用例** | 公开研究数据集 | 主力题库 |
| **APPS** | 约 1 万题，含测试用例与难度 | 公开研究数据集 | 主力题库，含大量中文/长题面 |
| **Codeforces Problemset API** | 题目、标签、难度 rating | 官方公开 API | 元数据补充（难度/算法标签） |
| AtCoder / Kattis / OpenJudge | 题库 | 公开站点，遵守 ToS | 扩展 |
| 洛谷 / 牛客 | 中文题库 | **需谨慎，遵守条款** | 仅作参考，不建议批量抓取 |

### 2.2 建议的起跑组合

```
HumanEval / MBPP  →  打通判题与诊断链路（小而干净，1–2 天）
CodeContests      →  规模化成主力题库（自带测试用例，无需自己造题）
Codeforces API    →  补难度与算法标签，用于推荐与掌握度建模
```

**关键优势**：这些数据集**自带测试用例**，意味着「题目正确性」和「标准答案」都不用你操心，验证器直接可用。

### 2.3 合规边界

- 只使用公开研究数据集与官方 API，遵守各自的 rate limit 与使用条款
- 不抓取需要登录或付费才能看到的判题结果
- 数据集在 README 中注明来源与许可

## 三、验证器设计（可插拔接口）

### 3.1 接口抽象

```python
from dataclasses import dataclass
from enum import Enum
from typing import Protocol

class Verdict(str, Enum):
    AC = "AC"    # 通过
    WA = "WA"    # 答案错误
    TLE = "TLE"  # 超时
    MLE = "MLE"  # 内存超限
    RE = "RE"    # 运行时错误
    CE = "CE"    # 编译错误

@dataclass
class CaseResult:
    case_id: str
    verdict: Verdict
    expected: str | None = None
    actual: str | None = None
    time_ms: int = 0
    memory_kb: int = 0
    stderr: str = ""

@dataclass
class RunReport:
    verdict: Verdict
    cases: list[CaseResult]
    compile_error: str | None = None

class Verifier(Protocol):
    """所有验证器的统一接口，领域可插拔。"""
    name: str

    def run(self, source: str, problem: "Problem", timeout_s: float = 3.0) -> RunReport:
        ...
```

### 3.2 判题沙箱（这块是工程深度所在）

必须做到，不是可选项：

- **隔离**：Docker 容器 / 独立进程，每次判题全新环境
- **无网络**：禁止访问外网
- **只读文件系统**：仅挂载临时工作区
- **资源限制**：CPU 时间、内存上限、进程数上限（防 fork bomb）、输出大小上限（防无限打印）
- **超时**：同时限制单用例与总时长，区分 TLE 与 RE
- **多语言**：至少 Python / C++ / Java 三种，覆盖大多数学生提交

**面试价值**：能讲清楚「怎么防止用户提交恶意代码打挂判题机」，这是真实工程问题，很多应届生答不上来。

### 3.3 三类验证器实现

| 验证器 | 作用 | 用在项目哪一步 |
| --- | --- | --- |
| `CodeVerifier` | 跑题目自带测试用例，给 AC/WA/TLE 判定 | 判题主链路 |
| `MutationVerifier` | 跑注入变异的代码，确认错因假设成立 | 评测集构建 + 诊断验证 |
| `ClaimVerifier` | 验证 Agent 讲解中的技术断言 | 讲解可信性（见第五节） |

## 四、自动评测集构建（核心方法）

### 4.1 正确性标签：自动生成

不人工标注，用**对拍**得到标准答案：

1. 准备参考解法（数据集自带或自己写）
2. 生成测试输入：随机输入 + 边界输入（极值、空集、单元素、重复元素、大数、溢出边界）
3. 参考解法 vs 暴力解法对拍，两者一致才认为该用例可信
4. 不一致的用例标记为可疑，整题剔除

### 4.2 错因标签：变异测试自动构造

这是整套方案最关键的一步。**故意注入已知类型的错误，注入的是什么错，标签就是什么错。**

| 变异算子 | 示例（原 → 变异） | 错因标签 |
| --- | --- | --- |
| 边界条件 | `i < n` → `i <= n` | 循环边界错误 |
| 差一错误 | `ans + 1` → `ans + 2` | 计数偏移 |
| 运算符替换 | `a + b` → `a - b` | 运算符号使用错误 |
| 比较取反 | `if x > 0` → `if x >= 0` | 边界/条件判断错误 |
| 条件取反 | `if flag` → `if not flag` | 逻辑取反错误 |
| 初始化错误 | `ans = 0` → `ans = 1` | 初始化值错误 |
| 提前返回 | 删除 `break` / 提前 `return` | 控制流错误 |
| 变量交换 | `f(a, b)` → `f(b, a)` | 参数顺序错误 |
| 索引方向 | `arr[i]` → `arr[n-1-i]` | 索引方向错误 |
| 类型/精度 | 整除 → 浮点，`int` → `float` | 精度与类型错误 |

### 4.3 生成流水线

```
题目 + 参考解法
      │
      ├─ 变异算子 ×N ──→ 候选错误代码
      │                        │
      │                        ▼
      │                  跑 CodeVerifier
      │                        │
      │            ┌───────────┴───────────┐
      │        判为 AC                判为 WA/TLE
      │       （等价变异，丢弃）     （有效样本，保留）
      │                                  │
      ▼                                  ▼
  正常样本                    (错误代码, 正确解法, 错因标签, 失败用例)
```

**只保留「确实被判错」的变异体**——这保证了标签的真实性：不是人为假设它会错，而是判题机证明它错了。

### 4.4 目标规模

| 数据集 | 规模 | 用途 |
| --- | --- | --- |
| 正确性评测集 | 5,000–10,000 条 | 判题链路回归 |
| 错因评测集 | 3,000–5,000 条，覆盖 8–10 类错因 | 诊断准确率评测 |
| 人工抽检 | 100 条 | 验证自动标签质量（报告一致率） |

## 五、杀手锏：讲解可信性验证

大模型讲题最大的问题是**会一本正经地讲错**。这个方案可以把它也变成可验证的：

### 5.1 反向注入验证（核心）

```
学生错误代码 + Agent 的错因假设「你的循环边界写错了」
        │
        ▼
把假设反向修复回代码（i <= n 改回 i < n）
        │
        ▼
跑 CodeVerifier
        │
   ┌────┴────┐
 通过        仍不通过
   │            │
假设成立      假设不成立，讲解是错的 → 重做
```

**这套机制让「讲解对不对」也由判题机裁决，而不是靠人信不信。** 面试时讲这一点，效果会很明显。

### 5.2 辅助一致性检查

- 讲解中提到的行号、变量名必须真实存在于提交的代码中
- 讲解引用的失败用例必须来自真实的判题结果
- 讲解给出的修复代码必须能通过全部测试用例（不通过则不允许输出）

## 六、多 Agent 编排

| Agent | 职责 | 调用什么工具 |
| --- | --- | --- |
| **Judge** | 编译、运行、汇总判定 | 判题沙箱 |
| **Diagnoser** | 基于失败用例与变异库定位错因 | MutationVerifier、静态分析 |
| **Explainer** | 生成分步讲解与修复建议 | LLM |
| **ClaimVerifier** | 校验讲解中的技术断言 | ClaimVerifier（反向注入） |
| **Coach** | 根据掌握度画像推荐下一题 | 题库检索、用户历史 |

编排链路：`Judge → Diagnoser → Explainer → ClaimVerifier →(不通过则回到 Explainer) → Coach`

**这一步天然满足 JD 里的「任务分解、分配与结果整合」和「校验失败自动重做」。**

## 八、第一周执行清单

| 天 | 任务 | 交付物 |
| --- | --- | --- |
| **Day 1** | 拉取 HumanEval + MBPP，搭最小判题循环（本地进程执行即可） | 能对 10 道题跑出 AC/WA |
| **Day 2** | 把判题搬进 Docker 沙箱：无网络、资源限制、超时、多语言 | 沙箱跑通 Python + C++ |
| **Day 3** | 实现 `Verifier` 接口与 `CodeVerifier`，接入 CodeContests 扩到 500 题 | 判题成功率报告 |
| **Day 4** | 实现 5 个变异算子，跑出第一批错因样本 | 约几百条带标签数据 |
| **Day 5** | 补齐到 10 个算子，统计各类错因的样本分布与有效率 | 错因数据集 v1 + 分布图 |
| **Day 6** | **找 3 个真实用户**：同门里在刷题/准备面试的同学，问他们现在怎么debug | 用户需求记录 |
| **Day 7** | 定义 baseline 指标，跑通「判题 → 错因 → 讲解」最小闭环 | 端到端 demo + 指标基线 |

> Day 6 不要往后拖。**用户是唯一买不到的资源**，越早锁定越好。

## 九、必须记录的指标

**判题层**

- 判题成功率、平均判题耗时、沙箱逃逸/异常次数
- 支持语言数、单题用例数

**诊断层**

- 错因诊断准确率（在自动生成的错因评测集上）
- 各类错因的召回率（哪类错因最容易判错）
- 覆盖率：能识别多少种错因类型

**讲解层（差异化指标）**

- **讲解可信率**：被 ClaimVerifier 判定为成立的讲解占比
- 修复建议的实际通过率（把建议代码真跑一遍）

**业务层**

- 真实用户数、周活跃、人均提交次数
- 用户调试时间变化（人工排查 vs 系统诊断）
- 用户对错因诊断的采纳率

## 十、面试会被追问的点

1. 怎么防止用户提交恶意代码打挂判题机？（沙箱设计）
2. 变异测试会产生大量等价变异（改了但结果不变），你怎么筛掉？
3. 错因标签是自动生成的，你怎么证明标签本身是对的？
4. 错因诊断准确率怎么算的？评测集多少条、怎么分布的？
5. 讲解的可信率是怎么定义的？反向注入一定能验证吗？有没有例外？
6. TLE 和 WA 混在一起时，错因诊断怎么办？
7. 多 Agent 比单 Agent 多花多少 token？ClaimVerifier 这一步值不值这个成本？
8. 用户提交的代码有隐私问题吗？

## 十一、风险与应对

| 风险 | 应对 |
| --- | --- |
| 变异算子产生的等价变异过多，样本有效率低 | 只保留被判错的变异体；先小规模测各算子的有效率，再决定加权 |
| 错因分类体系不够细，标签太粗 | 先做 8–10 类粗粒度错因，跑通后再细分 |
| 沙箱实现耗时超预期 | Day 1 先用本地进程跑通逻辑，Day 2 再上 Docker；不追求完美隔离 |
| 找不到真实用户 | Day 6 必须完成；退路是自用 + 开源发布收集真实 issue 反馈 |
| 范围膨胀（想做全语言、全题型） | 只做 Python + C++、只做算法题，其余一律列为扩展点 |
